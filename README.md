Цель — понимать устройство приложения, выполнять одну выбранную итерацию и сохранять проверяемый результат. Изучай проект последовательно, расширяя область чтения по обнаруженным зависимостям. Этот раздел дополняет правила итераций из разделов 15 и 19.9.

### 1. Сначала установи фактическое состояние

Перед выбором итерации найди актуальный `To do list` в README либо другом текстовом документе текущей ветки. Проверь ссылки README на отдельный файл плана и выполни поиск по актуальным текстовым документам репозитория. Упоминание названия списка в инструкции или журнале и исторический список из экспорта сами по себе не подтверждают наличие действующего плана.

**Если актуальный `To do list` нигде не найден, ничего не изменяй и не начинай итерацию: не придумывай задачи, не запускай сборку и тесты, не создавай коммиты, теги или публикации. Сообщи пользователю: «To do list не найден. Необходимо сформулировать To do list.»**

Определи рабочую ветку, исходный коммит, состояние рабочей копии и текущую версию. Учти пользовательские изменения и незавершённую работу предыдущей итерации.

Проверь `VERSION`, `package.json` и относящиеся к текущему состоянию поля `EXPORT-METADATA.json`. Различай происхождение экспорта и текущую версию приложения.

Подробности — в журнале раздела 18. Исходная редакция README без изменений сохранена в `docs/README-original.md`.

Дополнения относятся к передаче и локальному запуску:

## 2. Быстрый запуск

### Требования

- Node.js **22 или новее**, для разработки рекомендован Node.js 24. Проверено на Node.js `24.22.1`, npm `11.9.0`.
- PostgreSQL **17**; для локальной разработки подготовлен Compose с `postgres:17.11-bookworm` и отдельным тестовым экземпляром. Для Compose нужны Docker Engine и Docker Compose v2 с `up --wait`.
- Современный браузер с JavaScript и ES-модулями; интернет для Leaflet, картографических источников и первой установки npm/образа.

Работайте в корне репозитория, рядом с `package.json`. Установите зависимости по lockfile:

```bash
npm ci
```

Единственная прямая зависимость приложения — `pg@8.23.1`, используемая только в Node. Сборка Worker по-прежнему не требует подключения к БД и не включает драйвер/серверное окружение.

### Локальная БД и приложение

Скопируйте `.env.example` в `.env` (`cp .env.example .env`, в PowerShell — `Copy-Item .env.example .env`). Замените четыре значения `CHANGE_ME_*` собственными разными паролями. Пароль в `DATABASE_URL` должен соответствовать `POSTGRES_APP_PASSWORD`; зарезервированные символы URL нужно percent-кодировать. Локальные `.env` и `.env.test` исключены из Git.

С P08 `PUBLIC_ORIGIN` обязателен для Node: точный канонический origin браузера, например `http://127.0.0.1:3000`, без завершающего `/`, пути, query, fragment и учётных данных. При смене браузерного адреса/порта обновите и это значение; `HOST=0.0.0.0` — адрес прослушивания, а не публичный origin. В production нужен `https://ваш-домен` за HTTPS reverse proxy, даже если сам Node слушает локальный HTTP. `Host` и forwarding-заголовки не определяют origin или Secure. Необязательный `SESSION_TTL_SECONDS` — 300–604800, по умолчанию 604800 (7 суток). Шаблоны `.env.example`/`.env.test.example` обновлены; дополнительные миграции для P08 не нужны.

```bash
docker compose up -d --wait postgres
npm run db:check
npm run db:migrate
npm run build
npm test
npm start
```

Откройте **http://127.0.0.1:3000/**. `npm start` загружает `.env`; процесс должен оставаться открытым, остановка — `Ctrl+C`. До соединения с БД проверяются `PUBLIC_ORIGIN`/`SESSION_TTL_SECONDS`, `AUTH_*` и `TRUSTED_PROXY_CIDRS`, перед открытием HTTP выполняется `SELECT 1`. При отсутствии/неверной конфигурации или недоступной БД запуск завершается с понятным сообщением и кодом 1; URL, пароль и исходная ошибка драйвера не печатаются. `db:check` также проверяет соединение и всегда закрывает пул.

Compose публикует рабочую локальную БД только на `127.0.0.1:55432`, создаёт обычную роль `geokontekst` и БД `geokontekst`; роль не является суперпользователем и не создаёт другие роли/БД. Администратор `postgres` получает отдельный пароль. Данные хранятся в томе `postgres-data`; `tools/postgres-init.sh` выполняется только при его первой инициализации. Изменение паролей в `.env` не меняет уже созданные роли: для существующего тома пароль изменяют в PostgreSQL штатно.

Если PostgreSQL 17 уже установлен отдельно, Compose не нужен: укажите его URL и TLS-параметры в `.env`, затем выполните `npm run db:check` и остальные команды. P04/P05 добавили схему `users`/`sessions`, `images`/`layer_settings` и список `image_metadata`; Node API аккаунта реализованы P09–P12; серверная загрузка и привязка клиента к БД относятся к следующим шагам. Миграции запускаются явно, не при каждом старте HTTP.

### Отдельная тестовая БД

Скопируйте `.env.test.example` в `.env.test`; задайте в `TEST_DATABASE_URL` пароль из `TEST_POSTGRES_APP_PASSWORD` файла `.env`. Не используйте здесь рабочую строку подключения.

```bash
docker compose --profile test up -d --wait postgres-test
npm run db:migrate:test
npm run test:db
```

Тестовый экземпляр имеет отдельные контейнер, сеть, том `postgres-test-data`, порт `127.0.0.1:55433`, роль и имя БД `geokontekst_test`. Тестовая роль отсутствует в рабочем экземпляре. `test:db` загружает `.env.test` и требует `NODE_ENV=test` и `TEST_DATABASE_URL` с именем БД, оканчивающимся на `_test`. При наличии `DATABASE_URL` дополнительно проверяются отличия имени БД и роли; подключения к `DATABASE_URL` в тестовом режиме нет. Переменные, уже заданные в окружении процесса, имеют приоритет над env-файлом; неверный режим останавливает тесты.

`npm test` запускает 101 проверку без PostgreSQL, `npm run test:db` — 69 проверок PostgreSQL 17. Состав актуального набора — раздел 10. Миграционные тесты создают уникальные схемы `p04_test_<uuid>` и `p05_test_<uuid>` внутри подтверждённой тестовой БД и удаляют только эти схемы. Схема `public` и данные других тестовых схем не очищаются; HTTP-проверки Node удаляют только собственных пользователей с UUID-именами. Последующие API-тесты также создают отдельные схемы P07–P11.

### Миграции P04–P05

```bash
npm run db:migrate
```

Команда загружает `.env`, подключается к `DATABASE_URL` и применяет SQL из `migrations/`. Для отдельной тестовой БД используйте `npm run db:migrate:test`: загружается `.env.test`, обязательны `--test`, `NODE_ENV=test` и `TEST_DATABASE_URL`. Несогласованный режим останавливает команду до обращения к БД. Прямой запуск для уже заданного окружения: `node tools/migrate.mjs` или `node tools/migrate.mjs --test`; справка — `--help`.

Последовательность: `0001_users_sessions.sql`, затем `0002_images_layer_settings.sql`. На базе P04 команда применяет только второй файл; на чистой БД — оба. Успех печатает только количество новых/уже применённых миграций. Повторный запуск сохраняет таблицы, данные, идентификаторы и даты записей истории.

| Таблица | Поля и ограничения |
| --- | --- |
| `users` | `id` UUID с `gen_random_uuid()`, `email` text с уникальностью, `name` text (1–80 символов), непустой `password_hash` text (до 2048 символов), `created_at` timestamptz |
| `sessions` | `id` UUID, уникальный `token_hash` bytea ровно 32 байта (SHA-256), обязательный `user_id` → `users.id`, `created_at`/`expires_at` timestamptz; истечение позже создания |
| `schema_migrations` | `version`, имя SQL-файла, `checksum` SHA-256 и дата применения; версия/имя уникальны |
| `images` | UUID, обязательный `user_id`, имя/MIME, `file_data` bytea, вычисляемый `size_bytes`, размеры, WGS84-границы, угол, прозрачность, фиксация, ревизия и даты |
| `layer_settings` | Одна строка на `user_id`, общая прозрачность (по умолчанию 1), ревизия и даты |
| `image_metadata` (view) | Явная выборка метаданных `images` без `file_data`; используется для обычного списка |

БД перед INSERT/UPDATE email удаляет краевые обычные пробелы и приводит значение к нижнему регистру через `pg_c_utf8` (Unicode simple lowercase PostgreSQL 17, без зависимости от системной locale). CHECK закрепляет каноническое хранение, UNIQUE запрещает коллизии, включая параллельные записи. Нужна кодировка БД **UTF8**. С P07 серверные функции `validateRegistration`/`validateLogin` в `src/backend/account-validation.mjs` одинаково проверяют и нормализуют email через `trim().toLowerCase()`. `src/backend/passwords.mjs` создаёт `password_hash` с версией, солью и параметрами `scrypt`; формат и порядок вызова — в разделе 19.2. Проверены сохранение/поиск нормализованных Unicode-адресов и хеша в существующей схеме. P09/P10 подключили эти функции к HTTP-регистрации и входу с защитой P08.

Сессия не существует без пользователя: внешний ключ отклоняет неизвестный UUID, удаление пользователя каскадно удаляет его сессии. Помимо первичных/уникальных индексов есть индексы по `sessions.user_id` и `sessions.expires_at` для поиска/отзыва/очистки. С P08 `src/backend/sessions.mjs` выпускает/проверяет/отзывает сессии, хранит только SHA-256 токена и срок, а HTTP-guard требует действующую сессию до личного запроса. P11 подключила профиль/выход и отдельную команду очистки истёкших записей; HTTP-регистрация P09 создаёт сессию вместе с аккаунтом; вход P10 проверяет пароль и выдаёт новую сессию, не изменяя пользователя/настройку слоя.

P05 хранит байты и параметры изображения одной строкой `images`. `size_bytes` — `GENERATED ALWAYS AS (octet_length(file_data)) STORED`: он автоматически совпадает с байтами и не задаётся в INSERT/PATCH. Для списка используйте `SELECT ... FROM image_metadata WHERE user_id = $1 ORDER BY created_at, id`; представление не выбирает `file_data`, а размер уже хранится отдельно. Байты читаются отдельным запросом по ID и владельцу из `images`. Поиск списка поддерживает индекс `(user_id, created_at, id)`. Представление работает с правами вызывающего (`security_invoker`). Проверка сессии в HTTP-API подключена в P08; ограничения записей по владельцу будут добавлены в P17–P20. Само представление не подменяет авторизацию.

| Значение в БД P05 | Ограничение |
| --- | --- |
| Имя/MIME | Базовое непустое имя до 255 Unicode-символов без путей/управляющих символов; PNG/JPEG/WebP |
| Файл | bytea от 1 до 20 971 520 байт; размер вычисляется БД |
| Размеры | width/height 1–16384, произведение до 40 000 000 (вычисляется через bigint без переполнения) |
| Границы | Четыре double precision: `south, west, north, east`; `-85 ≤ south < north ≤ 85`, `-180 ≤ west < east ≤ 180`; NaN/Infinity отклоняются |
| Параметры | angle — целое −180…180, opacity — конечное 0…1, locked — обязательный boolean; начальные значения 0 / 0.65 / false |
| Ревизия/даты | Положительная integer-ревизия (по умолчанию 1); конечные timestamptz, updated_at не раньше created_at |

В API `bounds` собирается как `[[south,west],[north,east]]`; параметры других форматов в БД не сохраняются. Проверка реального содержимого/декодирования и соответствия MIME/размеров относится к P18; SQL ограничивает метаданные и байты, но не декодирует изображение. Обновление ревизии и updated_at будущие запросы P21/P27 выполняют явно, одновременно с изменением параметров.

Миграция P05 создаёт `layer_settings` с opacity=1/revision=1 для уже существующих пользователей, включая пустой слой. Для новых аккаунтов P09 создаёт настройку в транзакции регистрации; автоматического триггера на INSERT пользователя нет. Общая прозрачность хранится независимо от индивидуальной и не меняет её. Внешние ключи отклоняют неизвестного владельца, удаление пользователя каскадно удаляет изображения с байтами и настройки. Имена файлов не уникальны: одинаковые файлы/имена допускаются, как предусмотрено контрактом загрузки.

Каждый новый шаг добавляйте отдельным файлом `0003_<название>.sql`, затем `0004_...` без пропусков/повторов: имя после номера содержит только строчные латинские буквы, цифры и подчёркивания. SQL читается как UTF8; CRLF приводится к LF до исполнения и вычисления SHA-256, поэтому переносы строк Windows/Linux не меняют историю. Файлы — доверенный SQL проекта; не помещайте в них секреты или собственные BEGIN/COMMIT. Исполнитель держит advisory lock на одном соединении, проверяет историю и оборачивает каждый файл вместе с записью истории в транзакцию. Ошибка/разрыв соединения откатывает неподтверждённый шаг; ранее применённые шаги сохраняются. После устранения причины повторите ту же команду. Изменение, переименование или отсутствие уже применённого файла останавливает запуск по контрольной сумме/истории; исправления вносятся новой миграцией. Автоматических down-миграций и очистки данных нет. Ожидание блокировки и выполнение SQL ограничены `DB_STATEMENT_TIMEOUT_MS`.

### Лимиты авторизации и доверенные proxy P12

По умолчанию один Node-процесс допускает за окно 900 секунд **5 попыток регистрации на IP** и **10 попыток входа на пару IP/нормализованный email**. Настройки AUTH_WINDOW_SECONDS, AUTH_REGISTER_MAX_ATTEMPTS и AUTH_LOGIN_MAX_ATTEMPTS — десятичные целые 1–2147483647, без пробелов/ведущих нулей; ноль не отключает лимит. Неверная конфигурация останавливает запуск до SQL/HTTP; шаблоны .env обновлены. Новых npm-зависимостей или миграций нет.

Порядок: метод → Origin → опциональная сессия → ограниченный JSON/валидация полей → резервирование попытки → scrypt/прикладной SQL. Считаются все допущенные попытки, включая успех, неверные учётные данные, коллизию email и ошибку БД; ошибочные поля/JSON/media/размер/Origin попытку не расходуют. Ответ сверх лимита — 429 RATE_LIMITED, Retry-After с округлённым вверх остатком секунд, private,no-store, без Set-Cookie. Для этого запроса scrypt и прикладной SQL аккаунта не запускаются; прежний guard может читать действующую cookie до лимитера. Существующая сессия не отзывается. Me/logout, личные API и геоданные не расходуют эти счётчики.

Окно начинается с первой попытки конкретного ключа. Успех не сбрасывает счётчик, блокированные запросы не продлевают окно, после истечения попытки вновь доступны. В памяти не более 10 000 ключей суммарно; сохраняются SHA-256 идентификаторов и счётчики, без паролей/cookie/token/сырой почты. Истёкшие ключи убираются при обращении. При заполнении активные ограничения не вытесняются: новым ключам возвращается 429 до ближайшего освобождения места. Часы монотонные, резервирование синхронное до асинхронной работы. Перезапуск очищает счётчики, сессии в PostgreSQL сохраняются. Для нескольких Node-процессов потребуется общее хранилище лимитов.

TRUSTED_PROXY_CIDRS по умолчанию пуст: IP берётся только из incoming.socket.remoteAddress; клиентские заголовки не влияют на ключ. Для proxy задайте до 128 IPv4/IPv6 CIDR через запятую (не имена/порты), например 127.0.0.1/32,::1/128 для локального proxy. Разрешайте адреса самих proxy в своей схеме размещения. Proxy должен перезаписывать X-Forwarded-For либо добавлять проверенный адрес непосредственного отправителя. При доверенном TCP-пире используется **только X-Forwarded-For**: цепочка обходится справа налево через доверенные узлы до первого недоверенного IP; подставленный левый префикс за этим узлом не выбирает клиента. IPv6 нормализуется, IPv4 и IPv4-mapped IPv6 имеют общий ключ. До 32 адресов/4096 символов; адреса без портов/кавычек/zone ID. При отсутствии цепочки используется TCP-адрес proxy. Неверный необходимый для обхода адрес, пустая цепочка или превышение пределов дают 400 VALIDATION_ERROR до KDF/прикладного SQL; испорченный заголовок не переключает клиента на новую корзину. Неиспользуемый левый префикс после найденного недоверенного IP не разбирается. Forwarded/X-Real-IP/X-Forwarded-Host/X-Forwarded-Proto не задают IP; Host и forwarding не меняют PUBLIC_ORIGIN/Secure. Пароли, cookie, token и строка БД в логи лимитера не записываются.

### Очистка истёкших сессий P11

```bash
npm run db:sessions:cleanup
# Только отдельная тестовая БД:
npm run db:sessions:cleanup:test
```

Команда выполняет один атомарный пакет: удаляет до 1000 строк sessions с expires_at ≤ CURRENT_TIMESTAMP PostgreSQL, в порядке expires_at/id; активные сессии, пользователи и изображения не меняются. Заблокированные строки пропускаются через FOR UPDATE SKIP LOCKED и попадают в следующий запуск. Ноль удалений — нормальный результат, в том числе при чужой блокировке. При большом остатке повторите команду; вывод содержит только число удалённых строк. Ошибка даёт ненулевой код без SQL/реквизитов, пул закрывается.

Для размещения настройте запуск раз в минуту средствами планировщика ОС: из корня репозитория, с тем же серверным .env и абсолютным путём к npm/Node. Планировщик этой итерацией не устанавливается; автоматического таймера внутри HTTP-процесса нет. С задержкой очистки истёкшие записи занимают место, но не дают доступа: срок проверяется PostgreSQL при каждом разрешении сессии. GET me и прочие запросы чтения ничего не удаляют и не продлевают срок. Прямой CLI принимает уже заданное окружение: node tools/cleanup-sessions.mjs [--test]; --test требует NODE_ENV=test/TEST_DATABASE_URL, без отката к рабочей БД. --help работает без соединения.

### Серверное окружение P03

| Переменная | Поведение |
| --- | --- |
| `NODE_ENV` | `development` по умолчанию; допустимы `development`, `test`, `production` |
| `DATABASE_URL` | Обязательна для обычного Node-запуска; `postgresql://user:password@host:port/database` или `postgres://...` |
| `TEST_DATABASE_URL` | Единственный источник соединения при `NODE_ENV=test`; без отката к рабочей БД |
| `DATABASE_SSL` | `verify` по умолчанию, с проверкой сертификата; `disable` только для локальной/доверенной закрытой сети, как в примере Compose |
| `DATABASE_CA_FILE` | Необязательный CA при `verify`; ошибка чтения/пустой файл останавливают запуск |
| `DB_POOL_MAX` | По умолчанию 5, целое 1–20 |
| `DB_CONNECT_TIMEOUT_MS` | По умолчанию 5000, положительное целое до 2147483647 |
| `DB_STATEMENT_TIMEOUT_MS` | По умолчанию 10000, положительное целое до 2147483647; серверный таймаут SQL |
| `HOST`, `PORT` | `127.0.0.1`, `3000`; аргументы `--host`/`--port` имеют приоритет |

В URI нужны явные пользователь, пароль, сервер и имя БД. Query/fragment не поддерживаются: параметры TLS и таймауты задаются отдельными переменными и не могут быть переопределены через `sslmode` в URL. Другие переменные будущих аккаунтов перечислены в разделе 19.7; в P03 они ещё не используются. Серверные env-файлы и `src/backend/` не раздаются HTTP-адаптером.

После изменения `src/` или `build.mjs` остановите сервер, выполните `npm run build`, запустите заново и обновите страницу. Hot reload нет. После изменения Node-модулей достаточно перезапустить Node; после изменения зависимостей выполните `npm ci`.

```bash
npm start -- --port 3001
npm start -- --host 0.0.0.0 --port 3000
```

## 3. Функции действующей итерации

### Карта

Начальный центр — `[54.6296, 39.7420]`, масштаб — `15`. Используются Leaflet 1.9.4, масштабная линейка, кнопки приближения и отображение координат курсора.

Доступны три независимо включаемые подложки с собственной прозрачностью:

| Подложка | Источник | Начальное состояние |
| --- | --- | --- |
| Обычная карта | OpenStreetMap | Включена, прозрачность 1 |
| Спутник | Esri World Imagery | Выключена, настройка прозрачности 0.65 |
| Рельеф | OpenTopoMap | Выключена, настройка прозрачности 0.75 |

Левая панель слоёв и правая панель сведений сворачиваются. После изменения панелей выполняется `map.invalidateSize()`. В шапке — название, поиск и кнопка «О проекте / НИР», открывающая информационную панель. Подпись «предпроектный анализ» удалена в P02 согласно уточнённому описанию этого пункта в базовом коммите.

### Кадастровые участки

- Включены при открытии, исходная прозрачность `0.9`.
- Видимые границы текущий клиент получает растровым экспортом **слоя 32** открытой демонстрационной карты CoGIS / DataEast.
- При масштабе меньше `14` кадастровый растр не загружается; интерфейс предлагает приблизить карту.
- Нажатие на карту одновременно запрашивает участок из архивного ArcGIS-источника и серверного адаптера НСПД. Для запроса по клику требуется масштаб не меньше `13`.
- `Promise.any` выбирает первый успешный ответ, затем второй запрос отменяется. Поля двух ответов не объединяются.
- Полученная геометрия выделяется; атрибуты показываются справа.
- Карточка содержит номер, адрес, площадь, категорию земли, ВРИ, статус, стоимость и дату данных, если источник их передал.
- Для архивного ответа показывается его природа и дата выгрузки. Отсутствующие атрибуты не подменяются вымышленными сведениями.
- Разворачивание свойств обходит до 80 записей; подробная таблица показывает первые 36.

### Поиск

Точный номер участка вида `62:29:0040006:531` запускает поиск одновременно по архивному источнику и НСПД. Пробелы из номера удаляются. При успехе карта приближается к участку.

Остальной ввод рассматривается как адрес и отправляется браузером в Nominatim с `limit=1` и русским языком. Автоматического ограничения геокодирования границами Рязани нет, поэтому лучше вводить город вместе с адресом.

Серверный поиск НСПД допускает и номер квартала из трёх групп, но интерфейс определяет кадастровый запрос по четырём группам номера участка. Трёхгруппный ввод в текущей форме пойдёт в адресный поиск.

### Генплан

Слой включён при открытии с прозрачностью `0.62`. Оригинальный JPEG **2048×1928** находится в `src/genplan.jpg`. Доступны скрытие/показ и изменение прозрачности. Геопривязка вычисляется в `src/genplan-calibration.mjs`.

Сборка встраивает исходные байты JPEG в Worker через base64; маршрут `/genplan.jpg` отдаёт их без повторного JPEG-сжатия.

### Пользовательские изображения

- Можно выбрать несколько PNG, JPEG или WebP.
- Один файл — до **20 МиБ** (`20 * 1024 * 1024` байт).
- Изображение первоначально размещается в центре текущего вида карты с сохранением соотношения сторон.
- Центральный маркер перемещает слой; угловые маркеры изменяют размер.
- Доступны поворот `−180…180°` с шагом `1°`, прозрачность, фиксация, разблокировка, переход к слою и удаление.
- Код использует `URL.createObjectURL` и не отправляет загруженные изображения на сервер.
- Состояние существует в памяти вкладки. После перезагрузки изображения и их настройки не восстанавливаются. Сохранение проекта/геопривязки в файл в этой версии не реализовано.

## 4. Границы реализации

## 6. Архитектура и сборка

Клиент написан на обычном JavaScript и Leaflet. React, Vite, TypeScript и внешний npm-сборщик не используются.

Сервер — объект `export default` с асинхронным `fetch(request)` в формате Cloudflare Worker. Он использует Web API (`Request`, `Response`, `fetch`, `ReadableStream`, `AbortController`). Базы D1, R2, KV и другие bindings не требуются.

`npm run build`:

1. Создаёт `dist/server/` и `dist/.openai/`.
2. Читает HTML, клиентский JS, геомодуль, калибровку и серверный модуль.
3. Кодирует оригинальный JPEG в base64.
4. Формирует `dist/server/index.js`: сервер, клиентские строковые константы, JPEG и маршрутизатор.
5. Копирует `.openai/hosting.json` в сборку.

Сборка не скачивает карты и не запрашивает кадастр. Интернет для неё не нужен. При исходном экспорте повторная сборка дала тот же SHA-256 Worker, что и исходный коммит. В P12 Worker побайтово совпадает с P11; Node-модули в сборку не входят.

С P03 Node-адаптер до открытия HTTP проверяет PostgreSQL через отдельный `src/backend/database.mjs`. Пул закрывается при SIGINT/SIGTERM и ошибке HTTP-прослушивания; сырые ошибки драйвера не печатаются. До старта читается доверенная конфигурация авторизации; после успешного старта `createRequestHandler` сначала вызывает `createNodeApiHandler` с обязательным `createAuthenticationGuard`. Только ответ `null` передаёт запрос прежнему Worker; его тело до этого не читается. Пространства аккаунта, изображений и настроек слоя принадлежат Node.

Для прежних маршрутов локальный адаптер преобразует Node HTTP-запрос в стандартный `Request` и вызывает готовый `worker.fetch`. Для новых маршрутов Node-маршрутизатор возвращает собственный `Response`. Ответы передаются потоково. Это не статическая публикация каталога: README, история, метаданные и исходные файлы через него не раздаются.

## 7. Серверный API

Описанные ниже географические API Worker принимают `GET`. Другой метод возвращает прежний `405`, неизвестный API-маршрут вне новых пространств — прежний `404`.

### Новые API Node (P06–P12)

Пространства `/api/auth`, `/api/images`, `/api/layer-settings` с границей сегмента обрабатываются до Worker. Неизвестный путь внутри пространства даёт `404 NOT_FOUND`; неверный метод — `405 METHOD_NOT_ALLOWED` с `Allow`. Пути и методы заданы в таблице 19.4, завершающий `/` не является псевдонимом маршрута. Остальные запросы, включая геоданные и ресурсы карты, проходят прежнему Worker без чтения тела новым маршрутизатором.

С P08 известный маршрут проверяет метод, затем Origin для POST/PATCH/DELETE, затем сессию и только после этого ID/тело. Изменяющий запрос без точного `Origin: PUBLIC_ORIGIN` получает **403 `ORIGIN_REJECTED`**; личный запрос без действующей cookie — **401 `AUTH_REQUIRED`**. Неизвестный/просроченный/отозванный токен доступа не даёт. Ошибка запроса PostgreSQL возвращает 503 и не превращается в гостя. Личный обработчик блокируется самим маршрутизатором и при пропущенном/неверном guard.

**P09: `POST /api/auth/register` работает.** После Origin/опциональной сессии и ограниченного JSON проверяются email/password/name, email нормализуется, имя сохраняется текстом. Пароль хешируется scrypt до получения соединения/BEGIN. Одна транзакция создаёт users, layer_settings с opacity=1/revision=1 и сессию, при смене аккаунта отзывает предыдущую сессию этого браузера. Только после подтверждённого COMMIT отправляются **201 `{user: {id, email, name}}`** и Set-Cookie. Пароль/хеш/соль/токен не включаются в JSON или лог.

Повторная нормализованная почта даёт **409 EMAIL_EXISTS** через ограничение users_email_key и `ON CONFLICT ... DO NOTHING`, в том числе при параллельных транзакциях. Ошибки полей — 400, типа — 415, размера — 413, Origin — 403, БД — 503. Ошибка записи откатывает пользователя/настройку/сессию и отзыв старой сессии; cookie не выдаётся. При потере подтверждения COMMIT результат в БД может быть полным созданием либо откатом: ответ 503 не сообщает успех, соединение уничтожается, автоматического повтора регистрации нет.

**P10: `POST /api/auth/login` работает.** Вход принимает только JSON `{email,password}` с Origin и лимитом 16 КиБ. Email нормализуется общим правилом, пользователь читается параметризованным запросом. Для известной/неизвестной почты и повреждённого хеша выполняется один scrypt P07; неверный пароль/неизвестная почта дают одинаковый **401 INVALID_CREDENTIALS** без cookie. Пароль не обрезается и не меняет регистр или Unicode-представление. Ошибка БД — 503, а не фиктивно неверные учётные данные.

Проверка пароля выполняется без удержания клиента/транзакции. После успеха короткая транзакция повторно читает ID/проверенный хеш и блокирует запись через FOR SHARE до COMMIT: удалённая запись или изменённый пароль не получают сессию по устаревшему снимку. Сервер создаёт новый token, отзывает предыдущую сессию текущего браузера и только после COMMIT возвращает **200 `{user:{id,email,name}}`** и новую cookie. Повторный вход заменяет token; другое устройство не отзывается. Пользователь и настройки слоя не перезаписываются. Ошибка/откат сохраняет прежнюю сессию; потерянный COMMIT ACK имеет те же ограничения, что у регистрации, без автоматического повтора.

**P11: GET /api/auth/me и POST /api/auth/logout работают.** Me возвращает **200 {user: {id,email,name}}** по действующей cookie либо **200 {user: null}** для отсутствующей/неверной/истёкшей/отозванной сессии и удалённого пользователя. Профиль читается заново, срок не продлевается, Set-Cookie не выдаётся. URL/Authorization/клиентский userId не задают пользователя.

Logout без тела требует точный Origin. Сервер сначала дожидается удаления текущего серверного session.id, затем возвращает **204 без тела** и очищает am_session с теми же Path/HttpOnly/SameSite/Secure, Max-Age=0 и прошедшим Expires. Другие устройства сохраняются; гость и повторный выход с прежней cookie также получают 204/очистку. SQL-ошибка при чтении или отзыве — 503 без успешного ответа/очистки cookie: запрос можно повторить. При потере подтверждения DELETE результат отзыва может быть неопределён, успех не объявляется. Очистка истёкших строк выполняется отдельной командой (раздел 2).

**P12: регистрация/вход ограничены по правилам раздела 2.** Лимитер вызывается после валидации полей, до scrypt и прикладного SQL; в tools/serve.mjs один экземпляр разделяют оба обработчика. Сверх лимита — 429 RATE_LIMITED с Retry-After, без новой/очищенной cookie и без изменения сессии. Параметры/доверенные CIDR проверяются до подключения к БД. Успех, 401/409/503 расходуют допущенную попытку; me/logout лимитами не блокируются. Логи не включают входные секреты.

CRUD изображений и настройки пока возвращают **501 NOT_IMPLEMENTED** после проверок; авторизованные частные заглушки отвечают до чтения загрузки. Форм аккаунта пока нет — P13/P14; все четыре API аккаунта доступны через Node.

Обработчик подключается в `createNodeApiHandler({database, handlers, beforeHandle})` по имени действия; `auth.register` и `auth.login` подключены к createRegistrationHandler/createLoginHandler из src/backend/registration.mjs и login.mjs; auth.me/auth.logout — к createMeHandler/createLogoutHandler из account-session.mjs. Общий transactions.mjs регистрации/входа возвращает результат только после подтверждённого COMMIT. В `tools/serve.mjs` к `beforeHandle(context)` подключён `createAuthenticationGuard`: Origin/сессия проверяются до тела и декодирования ID; проверенный пользователь доступен как `context.auth.user`, данные сессии — как `context.auth.session`. JSON аккаунта ограничен 16 КиБ, PATCH — 8 КиБ, multipart целиком — 21 МиБ; GET/DELETE/logout — 0 байт. Подсчитываются реальные байты потока, включая chunked; `Content-Length` используется также для раннего отказа. JSON должен быть объектом и корректным UTF-8; другие типы/charset и сжатые тела отклоняются с 415. Проверки полей аккаунта P07 подключены к регистрации P09 и входу P10 с защитой P08. Проверки UUID/файла/multipart metadata относятся к последующим пунктам.

Ошибки имеют вид `{error: {code, message, fields?}}`; все новые ответы получают `Cache-Control: private, no-store` и `X-Content-Type-Options: nosniff`. При раннем ответе с непрочитанным телом соединение закрывается после передачи ответа; поток не дочитывается без ограничения. Несколько `Set-Cookie` передаются отдельными заголовками. Технические исключения не включаются в JSON или лог HTTP-адаптера. Параметры подключения к БД и код новых модулей не входят в Worker/клиент.

### OSM-объекты

```text
GET /api/objects?kind=buildings&bbox=54.629,39.739,54.632,39.745
```

Порядок `bbox`: **south,west,north,east** в географических градусах.

| `kind` | Выборка |
| --- | --- |
| `buildings` | Ways и multipolygon relations с `building` |
| `land` | Землепользование и `boundary=parcel` |
| `networks` | Трубопроводы, линии/кабели, подстанции, колодцы, гидранты и связанные объекты |
| `context` | `amenity`, `leisure`, `historic`, `public_transport`, `shop` |
| `roads` | Дороги и железные дороги |
| `nature` | Природные объекты, водотоки и охраняемые территории |

Ограничения области: разность широт до `0.08°`, долгот до `0.16°`, диапазоны `−85…85` по широте и `−180…180` по долготе. Порядок и конечность координат проверяются до сетевого обращения.

Успешный ответ содержит OSM `elements`, `source`, `endpoint`, `sourceDate`, `fetchedAt`, `cached`, `bounds`. Это не GeoJSON. Для преобразования используется `osmGeojson` из `src/geo.mjs`.

В Overpass-запросе заданы `timeout:20` и `maxsize:16777216`. HTTP-загрузка по умолчанию ограничена 25 секундами, JSON — 4 МиБ. Это разные ограничения разных стадий. Слишком большой ответ отклоняется.

### Поиск НСПД

```text
GET /api/cadastre/search?q=62%3A29%3A0040006%3A531
```

Проверяются формат и длина номера. Внешний маршрут: `/api/geoportal/v2/search/geoportal`, параметры `query` и `thematicSearchId=1`. Ответ нормализуется в FeatureCollection с `source` и `fetchedAt`.

### WMS-растр

```text
GET /api/cadastre/map?BBOX=4421000,7288000,4422000,7289000&WIDTH=256&HEIGHT=256
```

`BBOX` задаётся как `minX,minY,maxX,maxY` в **EPSG:3857**, в метрах. Ширина/высота — `1…2048`, размер области по каждой оси — до `250000` метров.

Используются `/api/aeggis/v3/36048/wms`, WMS 1.3.0, слой `36048`, CRS EPSG:3857, прозрачный PNG. Успех возвращает изображение, а не JSON.

### Определение участка

```text
GET /api/cadastre/identify?BBOX=4420000,7287000,4422000,7289000&WIDTH=800&HEIGHT=600&X=400&Y=300
```

`X/Y` — положение пикселя внутри изображения. Допускаются и `I/J`. Сервер отправляет WMS `GetFeatureInfo`, `I/J`, `QUERY_LAYERS=36048`, `FEATURE_COUNT=10`, `INFO_FORMAT=application/json`.

### Ошибки и кэш

Ошибки параметров/источника обычно дают `502`. Если до обработчика дошло `httpStatus=403`, он возвращает `503`. OSM-обёртка собирает отказы в общую ошибку: в исходном тесте `403` Overpass поэтому даёт `502`.

```json
{
  "error": "Описание ошибки",
  "unavailable": true,
  "at": "ISO-8601 timestamp"
}
```

Ошибка получает `Cache-Control: no-store`, успешный JSON — `private, max-age=60`, WMS-изображение — `private, max-age=300`. Отказ не маскируется пустой успешной выборкой.

OSM и кадастровый поиск кэшируются в памяти на пять минут, до четырёх ключей. При переполнении удаляется первый ключ Map. Одновременные запросы одного ключа используют общий незавершённый Promise. Это не постоянная и не распределённая база; перезапуск сбрасывает состояние. Таймаут запросов НСПД — 15 секунд.

## 9. Координаты и геопривязка

### Координаты

- Leaflet API: обычно `[latitude, longitude]`.
- GeoJSON: `[longitude, latitude]`.
- OSM API `bbox`: `south,west,north,east`, градусы.
- WMS `BBOX`: `minX,minY,maxX,maxY`, метры EPSG:3857.
- ArcGIS query запрашивает `outSR=4326`; клиент преобразует кольца в GeoJSON.
- `normalizeNspd` принимает EPSG:4326/CRS84 и преобразует из Mercator 3857/900913/102100. Неизвестная явно указанная CRS отклоняется; при отсутствии CRS большие координаты считаются признаком Mercator согласно исходной реализации.

### Геомодуль

`osmGeojson` преобразует nodes, ways и multipolygon relations. Сегменты колец соединяются с учётом направления, внутренние дворы сохраняются. Неполная геометрия увеличивает `skipped`, контуры не придумываются. В свойствах сохраняются OSM-теги, ссылка, дата и версия источника при их наличии.

`networkKind` различает электричество, газ, воду, канализацию, тепло и прочее. `layer=-1` не превращается в глубину заложения.

`areaM2` оценивает площадь Polygon/MultiPolygon с вычитанием отверстий. Эта оценка не заменяет кадастровую площадь.

Сохранённая `validateGeojson` принимает Feature/FeatureCollection с 1–50000 объектами, до 500000 координатных позиций, геометриями Point, MultiPoint, LineString, MultiLineString, Polygon, MultiPolygon в WGS84. GeometryCollection не поддерживается. В текущем интерфейсе эта функция к импорту не подключена.

### Калибровка генплана

| Ориентир | Пиксель `[x, y]` | `[longitude, latitude]` |
| --- | --- | --- |
| ВПП Дягилево, западный торец | `[392.48, 936.52]` | `[39.547355, 54.638319]` |
| ВПП Дягилево, восточный торец | `[559.80, 876.55]` | `[39.591597, 54.646555]` |
| Рязанский кремль, центр территории | `[1180.20, 950.40]` | `[39.7496288, 54.6362500]` |

Используется метод наименьших квадратов с независимым линейным масштабом/смещением по осям. Вертикальная координата рассчитывается в Web Mercator. Результат — юго-западный и северо-восточный углы JPEG. Поворот/сложная деформация листа алгоритмом не моделируются.

Исходный тест проверяет остаточные отклонения использованных опорных точек менее четырёх пикселей. Это проверка калибровки по этим точкам, а не независимая оценка точности по всему листу.

Порядок основных Leaflet panes: генплан `250`, архивный кадастр `425`, кадастровая группа `430`, выделение `440`, пользовательские рисунки `500`.

## 16. Решение проблем

| Симптом | Проверка / действие |
| --- | --- |
| Не найдены `node`/`npm` | Установка Node и PATH; после установки открыть терминал заново |

| Страница открыта через `file://` | Запустить адаптер и открыть HTTP-адрес |
| `L is not defined` / пустая карта | Проверить CDN unpkg и загрузку Leaflet в Network/Console |

### 19.1. Принятые решения и размещение

Целевой запуск — собственный Node.js-сервер с PostgreSQL. Клиент и API имеют один origin: локально `http://127.0.0.1:3000`, при размещении — один HTTPS-домен. Браузер не подключается к БД и не получает её реквизиты. Изображения, геопривязка и настройки доступны только владельцу; публичного каталога нет.

Для разработки использовать Node.js 24 и PostgreSQL 17, с фиксируемыми в P03 зависимостями/образом. Существующий адаптер требует Node.js 22 или новее; его минимальную версию этим документом не меняем. Драйвер — `pg` (node-postgres), пул соединений и параметризованные запросы. Файлы хранятся в `bytea` вместе с метаданными в PostgreSQL; PostGIS и отдельное файловое хранилище для этой задачи не требуются.

При размещении HTTPS reverse proxy направляет `/`, ресурсы и весь `/api/` на один Node-процесс. Он должен пропускать запрос загрузки до 21 МиБ, не кэшировать личные API и не направлять их на статический хостинг. PostgreSQL расположен на той же машине либо в закрытой сети; удалённое соединение использует TLS с проверкой сертификата. Данные БД находятся на постоянном диске/томе и входят в резервную копию. Для разработки достаточно локального PostgreSQL/Compose; для сайта нужен хостинг с постоянным Node-процессом и доступом к PostgreSQL. Поставщик, домен и публикация в P01 не выбираются и не создаются.

Применимость схемы к репозиторию подтверждена чтением `tools/serve.mjs` и `build.mjs`: есть работающий Node HTTP-вход и отдельный вызываемый Worker. Новые обработчики можно добавить перед ним, не меняя формат выдачи карты. Действующий Worker/Sites самостоятельно новые функции не обслуживает; добавление `pg` в конкатенируемый `src/server.mjs` нарушило бы эту границу. Размещение полной новой версии на прежнем Sites потребует отдельной задачи интеграции, а целевой путь текущего плана — Node. В P03 добавлены отдельные Node-модули и проверено фактическое соединение с PostgreSQL 17.11; маршруты новых API ещё не реализованы.

Не встраивать в Worker |

Node обрабатывает точные пространства `/api/auth`, `/api/images` и `/api/layer-settings` с их допустимыми подмаршрутами. Географический `handleApi` сохраняет прежние маршруты, методы и формат ошибок; ниже описаны только новые API.

### 19.2. Поля аккаунта и правила доступа

JSON использует camelCase; названия столбцов БД могут быть snake_case. ID — серверные UUID, даты в API — ISO 8601 UTC. Клиент не выбирает ID владельца.

| Поле | Контракт |
| --- | --- |
| `email` | Строка; `trim().toLowerCase()`; от 3 до 254 Unicode-кодовых точек; ровно один `@`, непустые части, точка внутри доменной части, без пробелов/управляющих символов. Одинаковая нормализация при регистрации и входе, уникальность нормализованного значения в БД |
| `password` | Строка 12–128 Unicode-кодовых точек; не обрезать пробелы и не менять регистр/Unicode-представление. Одинаковые правила в формах и на сервере; без дополнительных требований к сочетанию классов символов |
| `name` | После `trim()` 1–80 Unicode-кодовых точек, без управляющих символов; может повторяться у разных аккаунтов. Выводить как текст, а не HTML |
| `User` | Только `{id, email, name}`; пароль, его хеш/соль и токены не возвращать |

Это правила формата регистрации, а не подтверждение владения почтой; отправка писем в эту итерацию/план не включена. С P07 src/backend/account-validation.mjs и passwords.mjs реализуют эти функции; P09 уже использует их в POST регистрации с защитой P08. P10 также использует их при входе; P11 подключила me/logout с тем же безопасным профилем.

| Функция P07 | Поведение |
| --- | --- |
| `validateRegistration(body)` | Только email/password/name; возвращает внутренние проверенные данные, нормализуя email/края имени |
| `validateLogin(body)` | Только email/password; та же нормализация email и политика пароля |
| `validatePassword(value)` | Проверяет 12–128 кодовых точек, не преобразует пароль; при ошибке 400 с публичным `fields.password` |
| `toPublicUser(row)` | Ровно строковые `{id, email, name}`; использовать для HTTP вместо записи БД или внутренних данных с паролем |
| `hashPassword(password)` | Асинхронный scrypt v1 с новой случайной солью 16 байт; возвращает строку для `users.password_hash` |
| `verifyPassword(password, storedHash)` | Boolean после scrypt и timingSafeEqual; для неизвестного аккаунта передавать null/undefined и обязательно выполнить тот же вызов |

Имя хранится текстом: строка с `<...>` остаётся строкой, а интерфейс P13/P14 должен выводить её через `textContent`, не `innerHTML`. Неизвестные поля/значения не отражаются в ошибках; форма/лишние поля используют фиксированное сообщение `fields._form`. Все строковые поля должны содержать корректный Unicode; одиночные UTF-16-суррогаты отклоняются, чтобы UTF-8 не подменял пароль. Пароль не проходит `trim`, смену регистра или NFC/NFD; пробелы/кодовые точки считаются буквально. Внутренний результат валидатора содержит пароль только для хеширования и не является HTTP-ответом.

Формат v1: `scrypt$v=1$N=131072,r=8,p=1,dkLen=32$<salt-base64url>$<key-base64url>`. Соль 16 байт и ключ 32 байта записываются в канонической base64url без padding; длина строки 103 ASCII-символа. Профиль `N=2^17, r=8, p=1` выбран по [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt), scrypt асинхронный через [node:crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback). Рабочая память алгоритма около 128 МиБ на активный вызов, `maxmem=256 МиБ` задаёт верхний предел отдельной операции, а не RAM всего процесса.

Проверяется точный разрешённый профиль v1; произвольные/ослабленные/чрезмерные параметры из БД не исполняются. Сравниваются 32-байтовые буферы через `timingSafeEqual`. Отсутствующий/повреждённый/неподдержанный хеш запускает один настоящий scrypt того же профиля с запасной солью и сравнение, затем возвращает false. Это не гарантирует одинаковое время всей SQL/HTTP-операции; P10 даёт одинаковый 401 INVALID_CREDENTIALS для неизвестной почты/неверного пароля, а P12 ограничит попытки. Криптографический сбой возвращается безопасным INTERNAL_ERROR без исходных деталей/секретов. Пароли/хеши/соли не отправляются в профиль или лог; временные буферы пароля и вычисленного ключа зануляются.

Регистрация создаёт пользователя, исходную настройку слоя и сессию согласованно. Значение `user_id` для всех операций берётся из действующей сессии. Все SQL-запросы с пользовательскими значениями параметризованы. Во всех операциях рисунка использовать условия по ID и владельцу; валидный чужой и отсутствующий UUID дают одинаковый 404 после проверки сессии. Некорректная форма UUID — 400.

### 19.3. Cookie-сессия и защита запросов

**Статус P08–P11:** сессии и Origin реализованы в Node, подключены в tools/serve.mjs; конечные ответы me/logout реализованы в P11 через account-session.mjs. Доверенная конфигурация — readAuthConfig из auth-config.mjs, хранилище — createSessionService из sessions.mjs, guard — createAuthenticationGuard из authentication.mjs. Router также требует identity у личного обработчика и при забытом guard. Регистрация P09 вызывает сервис сессий и выдаёт cookie; вход P10 также выдаёт новую cookie после проверки пароля; отдельного публичного API выпуска токенов нет.

| Функция P08 | Вход/результат |
| --- | --- |
| `readAuthConfig(env)` | Обязательный канонический PUBLIC_ORIGIN, HTTPS в production, TTL 300–604800; неизменяемая конфигурация или безопасная ошибка до HTTP |
| `sessions.issue(userId, {client?, replaceSessionId?})` | Владелец и предыдущая сессия из серверного контекста; атомарные INSERT/DELETE, результат `{id, userId, expiresAt, cookie}` только для внутреннего кода |
| `sessions.resolve(headers)` | Одна каноническая am_session; SELECT активной сессии, `{user, session}` без токена/хеша либо null; SQL-ошибка 503 |
| `sessions.revoke(sessionId, {client?})` | Отзыв текущей сервером определённой сессии, boolean; повтор безопасен, другие устройства не отзываются |
| `sessionCookie` / `clearSessionCookie` | Строка Set-Cookie с одинаковыми именем/Path/флагами; у новой cookie оставшийся Max-Age и Expires, у очистки Max-Age=0 |
| `createAuthenticationGuard` | Метод уже проверен router; затем Origin → сессия/401 → ID/тело; проверенная identity в context.auth |
| `createMeHandler` / `createLogoutHandler` (P11) | 200 с публичным профилем/явным гостем; отзыв текущей сессии и 204 с очисткой cookie, включая повтор |
| `cleanupExpiredSessions(database)` (P11) | Один атомарный пакет до 1000 истёкших строк по часам PostgreSQL, SKIP LOCKED; число удалений или безопасная ошибка |

`issue` одним SQL-выражением вставляет новый digest и удаляет предыдущий ID; ошибка или откат внешней транзакции сохраняет старую сессию. Переданный client принадлежит вызывающему коду: helper не коммитит и не освобождает его. P09 использует это для создания пользователя/настройки/сессии одной транзакцией. Полученная cookie направляется только в заголовок Set-Cookie, HTTP-профиль строится отдельно через toPublicUser.

Повторные/пустые/неверно закодированные cookie отвергаются; URL, Bearer и UUID сессии не заменяют token. SHA-256 вычисляется от канонической ASCII-строки 32-байтового nonce. Чтение проверяет expires_at по часам PostgreSQL, не продлевает срок и не удаляет истёкшие записи. Отдельный CLI P11 очищает их пакетами; периодический запуск задаётся снаружи (раздел 2). Max-Age округлён вниз по оставшемуся сроку и ограничен TTL. Secure зависит от PUBLIC_ORIGIN, включая HTTPS proxy с локальным HTTP к Node; Host/forwarding не используются. SQL-отказ не превращается в гостевое состояние. Новые конфигурация/модули не входят в Worker/браузер.

Сессионный токен — 32 случайных байта в base64url. В PostgreSQL сохраняются SHA-256 токена, `user_id` и абсолютное время истечения; открытый токен хранится только в cookie `am_session`. Срок по умолчанию — 7 суток, без автоматического продления. Вход/регистрация выдают новый токен; при замене действующей сессии текущего браузера прежний токен отзывается. Выход отзывает текущую сессию, но не другие устройства.

Cookie: `HttpOnly; SameSite=Lax; Path=/`, без `Domain`, `Max-Age` соответствует оставшемуся сроку; при HTTPS обязательно `Secure`. Очистка использует то же имя/путь и `Max-Age=0`. После истечения/отзыва/подделки личные API возвращают 401. `me` для отсутствующей или недействующей сессии возвращает 200 с `user: null`; при сбое БД — 503, а не фиктивного гостя.

Все новые POST/PATCH/DELETE, включая вход/регистрацию/выход, требуют заголовок `Origin`, точно совпадающий с `PUBLIC_ORIGIN`; отсутствующий, `null` или чужой origin отклоняется с 403 до изменения данных. Это выбранная защита от CSRF для одного origin. Чувствительные GET не изменяют прикладные данные. Клиент использует относительные URL и cookie того же origin; cross-origin CORS и хранение токена в `localStorage` не нужны.

Публичный origin не определять из `Host`/`X-Forwarded-Host` и внутреннего URL `http://localhost`, который сейчас создаёт адаптер. Proxy-заголовки учитывать только от явно разрешённых адресов reverse proxy. Ограничение попыток входа/регистрации реализовано P12 и не заменяет проверку сессии. Только X-Forwarded-For от доверенного TCP-пира определяет IP по правилам раздела 2; PUBLIC_ORIGIN/Secure от заголовков не зависят.

Все новые API, включая выдачу файлов и ошибки, получают `Cache-Control: private, no-store` и `X-Content-Type-Options: nosniff`. Пароли, cookie, токены, байты файлов и URL подключения не записывать в логи.

### 19.4. Контракты маршрутов

**Статус P06–P12:** регистрация P09 и вход P10 реализованы: соответственно 201/200 с безопасным профилем и новой cookie. Вход проверяет пароль, неизвестная почта/неверный пароль дают один 401 INVALID_CREDENTIALS. Маршруты/лимиты/ошибки и Origin/авторизация P08 подключены. P11 реализовала me с 200/профилем либо user:null и logout с 204/очисткой cookie. P12 ограничила регистрацию/вход и добавила 429/Retry-After. Операции изображений/настроек, права владельца и проверка файла — следующие пункты; допущенные заглушки 501. Личный гость получает 401, неверный Origin — 403. Текущее поведение — раздел 7.

`JSON` в таблице означает объект с `Content-Type: application/json`. Все поля тела, кроме явно необязательных, обязательны; неизвестные поля отклоняются с 400. Тела DELETE/выхода отсутствуют. Формат ошибок общий и приведён ниже.

| Метод и путь | Доступ | Вход | Успешный ответ |
| --- | --- | --- | --- |
| `POST /api/auth/register` | Гость или текущий пользователь; проверка Origin | JSON `{email, password, name}` | 201, `{user: User}` и новая cookie |
| `POST /api/auth/login` | Гость или текущий пользователь; проверка Origin | JSON `{email, password}` | 200, `{user: User}` и новая cookie |
| `GET /api/auth/me` | Любой | Без тела | 200, `{user: User}` либо `{user: null}` |
| `POST /api/auth/logout` | Любой; проверка Origin | Без тела | 204 без тела, cookie очищена; повторный выход также 204 |
| `POST /api/images` | Владелец по сессии; проверка Origin | multipart: ровно один `file` и строка JSON `metadata` | 201, `{image: Image}` |
| `GET /api/images` | Пользователь | Параметры `limit` и `cursor` необязательны | 200, `{images: Image[], nextCursor: string/null}` |
| `GET /api/images/:id/file` | Только владелец | UUID в пути, без тела | 200, исходные байты и подтверждённый `Content-Type` |
| `PATCH /api/images/:id` | Только владелец; проверка Origin | JSON: `revision` и хотя бы одно из `bounds, angle, opacity, locked` | 200, `{image: Image}` с новой ревизией |
| `DELETE /api/images/:id` | Только владелец; проверка Origin | UUID в пути, без тела | 204 без тела; повтор для отсутствующей/чужой записи — 404 |
| `GET /api/layer-settings` | Пользователь | Без тела | 200, `{settings: LayerSettings}` |
| `PATCH /api/layer-settings` | Пользователь; проверка Origin | JSON `{opacity, revision}` | 200, `{settings: LayerSettings}` с новой ревизией |

В `metadata` загрузки обязательны `bounds`, необязательны `angle` (0), `opacity` (0.65), `locked` (false). Имя/размеры/тип/размер байтов сервер определяет по файлу; `userId`/`user_id` не принимаются. Один запрос — один файл; при выборе нескольких клиент отправляет их отдельно. Запись файла и метаданных атомарна. Автоматический повтор POST после неопределённого сетевого результата не делать: сначала перечитать список и показать состояние; одинаковые имена файлов сами по себе не означают дубликат.

Список упорядочен по `createdAt ASC, id ASC` и не включает байты. `limit` по умолчанию 50, допустимо целое 1–100; `cursor` — непрозрачное для клиента представление последней пары даты/ID, проверяемое сервером. `nextCursor: null` означает конец. Любая страница по-прежнему ограничена владельцем; клиент восстановления читает страницы до конца.

`revision` — положительное целое, начальное значение 1. PATCH атомарно сравнивает текущую ревизию вместе с ID/владельцем и увеличивает её на 1. При устаревшей ревизии — 409 `REVISION_CONFLICT`; клиент перечитывает состояние и не повторяет старые изменения вслепую. Это относится и к общей настройке слоя. DELETE удаляет свою запись независимо от ревизии; незавершённые клиентские PATCH отменяются, поздний PATCH удалённого ID получает 404.

### 19.5. Данные изображений, слой и ограничения

`Image` — объект `{id, name, mimeType, sizeBytes, width, height, bounds, angle, opacity, locked, revision, createdAt, updatedAt, fileUrl}`. `fileUrl` — относительный защищённый путь `/api/images/:id/file`; это не публичная ссылка. Метаданные и файл доступны только владельцу. Байты в JSON, `user_id` и внутренние данные хранения не возвращаются.

`LayerSettings` — `{opacity, revision}`. Настройка создаётся при регистрации: `opacity: 1, revision: 1`. Хранится одна на пользователя, независимо от наличия рисунков.

| Значение | Допустимое поведение/ограничение |
| --- | --- |
| Форматы | PNG, JPEG, WebP; проверка сигнатуры, реального декодирования и соответствия заявленному MIME; SVG/HTML отклоняются |
| Размер файла | 1–20 971 520 байт, то есть до 20 МиБ включительно |
| Пиксельные размеры | Ширина/высота — положительные целые до 16 384 включительно; всего до 40 000 000 пикселей; только одиночный статичный кадр |
| Имя файла | Базовое имя без пути/управляющих символов, 1–255 Unicode-кодовых точек; не использовать как путь на диске/SQL; выводить как текст |
| `bounds` | `[[south, west], [north, east]]` в WGS84, то есть пары `[latitude, longitude]`; все числа конечны, `-85 ≤ south < north ≤ 85`, `-180 ≤ west < east ≤ 180`, без пересечения линии смены дат |
| `angle` | Целое от −180 до 180 включительно, начальное 0 |
| `opacity` | Конечное число 0–1 включительно, индивидуальное начальное 0.65, общая начальная 1; сервер не округляет под шаг UI 0.05 |
| `locked` | Только boolean; фиксирует редактирование в интерфейсе, не меняет право владельца удалить/разблокировать рисунок |
| Тело загрузки | До 22 020 096 байт (21 МиБ) вместе с multipart; JSON `metadata` до 8 КиБ, ровно два поля, без лишних файлов |
| Остальные тела | JSON аккаунта до 16 КиБ, PATCH рисунка/слоя до 8 КиБ, без тела у GET/DELETE/logout |
| Обработка потока | Считать фактические байты при чтении, не полагаться на `Content-Length`; при превышении остановить чтение до полного буферирования/декодирования |

Ограничения проверяются и в клиенте, и обязательно на сервере; размеры/пиксели проверяются до дорогой полной обработки. Данные файла и расположение сохраняются без повторного сжатия. Общий регулятор применяет `image.opacity × settings.opacity`; изменение общего значения не перезаписывает индивидуальные.

Рисунки занимают верхний слой картографических данных, маркеры их редактирования находятся над ними. Панели, формы и элементы управления картой остаются доступными. Гость видит добавление и общую прозрачность даже при пустом списке; активация открывает вход/регистрацию и не выполняет личную операцию. Имя в шапке не влияет на проверку доступа.

### 19.6. Ошибки новых API

Формат: `{"error":{"code":"VALIDATION_ERROR","message":"Проверьте поля","fields":{"email":"Некорректная почта"}}}`. `fields` необязателен и содержит только сообщения, без введённого пароля/токена/SQL. Клиент ориентируется на HTTP и стабильный `code`, а `message` показывает пользователю. Ошибки не возвращаются как успешный пустой список.

| HTTP | Код/сценарий |
| --- | --- |
| 400 | `VALIDATION_ERROR` — поля, JSON/multipart, UUID, cursor/revision, неподдержанные поля; `INVALID_IMAGE` — пустой/повреждённый файл, недопустимые пиксельные размеры/кадры |
| 401 | `AUTH_REQUIRED` — личный маршрут без действующей сессии; `INVALID_CREDENTIALS` — одинаковый ответ для неизвестной почты и неверного пароля |
| 403 | `ORIGIN_REJECTED` — Origin отсутствует/не совпадает; не использовать 403 для раскрытия чужого файла |
| 404 | `NOT_FOUND` — неизвестный новый маршрут или отсутствующее/чужое изображение |
| 405 | `METHOD_NOT_ALLOWED` — метод не из таблицы, с заголовком `Allow` |
| 409 | `EMAIL_EXISTS` — нормализованная почта занята; `REVISION_CONFLICT` — устаревшее изменение |
| 413 | `PAYLOAD_TOO_LARGE` — превышены лимиты байтов запроса/файла/metadata |
| 415 | `UNSUPPORTED_MEDIA_TYPE` — формат тела/файла не разрешён или заявленный MIME не совпадает с обнаруженным |
| 429 | `RATE_LIMITED` — лимит попыток регистрации/входа, с `Retry-After` в секундах |
| 503 | `DATABASE_UNAVAILABLE` — соединение/временная недоступность БД; не раскрывать реквизиты |
| 500 | `INTERNAL_ERROR` — непредвиденный сбой; HTTP-адаптер логирует только фиксированный код |
| 501 | `NOT_IMPLEMENTED` — временный ответ P06 до подключения соответствующего прикладного обработчика |

Для известного защищённого маршрута проверять сессию до чтения большого тела и поиска записи; для изменяющего запроса сначала проверить метод и Origin. При чтении/изменении чужого ID никакие поля, ревизия и байты чужой записи не возвращаются.

### 19.7. Серверное окружение и запуск

В P03 реализованы `NODE_ENV`, подключение БД, TLS/CA, пул и таймауты; `HOST`/`PORT` поддерживались адаптером ранее. P08 добавила обязательный PUBLIC_ORIGIN и SESSION_TTL_SECONDS; P12 реализовала AUTH_*/TRUSTED_PROXY_CIDRS в auth-rate-limit.mjs/client-address.mjs. Реализованные значения валидируются при старте; неверная конфигурация останавливает запуск. Точные текущие команды и ограничения URL находятся в разделе 2.

| Переменная | Назначение и значение |
| --- | --- |
| `NODE_ENV` | `development` / `test` / `production`; для размещения явно `production` |
| `HOST`, `PORT` | Существующие параметры адаптера; локальные значения `127.0.0.1` / `3000` сохраняются |
| `PUBLIC_ORIGIN` | Обязательный origin без пути/query/fragment/учётных данных, например `http://127.0.0.1:3000`; в production только HTTPS |
| `DATABASE_URL` | Обязательная серверная строка подключения к рабочей/локальной БД; не отдавать клиенту/логам и не записывать в Git |
| `TEST_DATABASE_URL` | Отдельная строка только для интеграционных тестов; автоматического отката к `DATABASE_URL` нет |
| `DATABASE_SSL` | `disable` только для локальной/закрытой доверенной сети; `verify` с проверкой сертификата для удалённого production-подключения |
| `DATABASE_CA_FILE` | Необязательный путь к CA для `DATABASE_SSL=verify`; сертификат сервера обязательно проверяется |
| `DB_POOL_MAX` | По умолчанию 5, целое 1–20 |
| `DB_CONNECT_TIMEOUT_MS`, `DB_STATEMENT_TIMEOUT_MS` | По умолчанию 5000 / 10000; положительные целые, таймаут не отключать нулём |
| `SESSION_TTL_SECONDS` | По умолчанию 604800 (7 суток), допустимо 300–604800 |
| `AUTH_WINDOW_SECONDS` | Окно лимитов P12, по умолчанию 900; целое 1–2147483647 секунд |
| `AUTH_LOGIN_MAX_ATTEMPTS`, `AUTH_REGISTER_MAX_ATTEMPTS` | По умолчанию 10 / 5 на окно; целые 1–2147483647. Вход — по паре IP/нормализованная почта, регистрация — по IP |
| `TRUSTED_PROXY_CIDRS` | По умолчанию пусто; до 128 IPv4/IPv6 CIDR через запятую. Только X-Forwarded-For при доверенном TCP-пире; цепочка/ограничения — раздел 2 |

В P03 добавлены `.env.example`, `.env.test.example`, lockfile, пул и Compose с PostgreSQL 17.11. Текущий порядок: `npm ci` → настроить `.env`/БД → `npm run db:check` → `npm run build` → `npm start`. Перед Node-запуском с P04 добавлена команда `npm run db:migrate`; сборка Worker по-прежнему выполняется без БД. С P08 Node читает PUBLIC_ORIGIN/SESSION_TTL_SECONDS, с P12 также AUTH_*/TRUSTED_PROXY_CIDRS; всё проверяется до соединения с БД/HTTP. Origin/Secure определяются только конфигурацией.

Лимитер P12 хранит до 10 000 хешированных ключей/счётчиков в памяти одного Node-процесса: при перезапуске они сбрасываются. Несколько серверных процессов потребуют общего хранилища лимитов и не входят в выбранный первоначальный способ размещения. Сессии и рисунки при перезапуске не теряются, поскольку находятся в PostgreSQL.

### 19.8. Изолированная проверка будущего API

Текущий набор P12: 101 проверка без PostgreSQL и 69 на настоящем PostgreSQL, включая 10 новых без БД и 7 интеграционных P12. Сохранены 13 исходных гео/Worker-тестов, регистрация/сессии/пул/миграции. Вход проверен по HTTP: верный/неверный/неизвестный пароль, одинаковый отказ и одна KDF-операция, нормализация, новая cookie/повторный вход, другое устройство, устаревший снимок/блокировка/ошибки. Команды/состав — раздел 10, результаты — журнал 18. Профиль/гость, выход/повтор/другое устройство, перезапуск Node, истечение/очистка, блокировки и ошибки БД проверены P11. P12 подтвердила 429/Retry-After/восстановление, независимые пары/IP, подмену proxy, конкурентные попытки, ноль KDF/прикладного SQL после отказа и безопасные логи реального Node; P30 собирает сквозной сценарий.

Интеграционные тесты запускаются только с `NODE_ENV=test` и явно заданным `TEST_DATABASE_URL`. База имеет отдельное имя с суффиксом `_test`, отдельную роль без прав на рабочую БД, отдельный порт/том в Compose. До миграций/очистки тестовый запуск проверяет имя и отличие целевой БД от рабочей; при отсутствии/совпадении конфигурации останавливается без очистки. Для API-тестов рабочая база никогда не используется как запасная. В тестовой БД применяются те же миграции, создаются A/B и контролируемые маленькие файлы; после прогона данные удаляются только там.

Минимальная матрица: гость (401 и открытие формы), регистрация/коллизия email/вход/выход/истечение сессии, неверный Origin, сохранение/восстановление байтов и всех параметров, запрет A/B по прямому ID, ошибки размеров/форматов, 409 при старой ревизии, удаление, отказ БД, отсутствие приватных данных после смены пользователя. Геоданные с подменёнными ответами и доступность живых картографических источников проверяются отдельно.

Основания технического выбора: [Node HTTP](https://nodejs.org/docs/latest-v24.x/api/http.html), [Node crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html), [PostgreSQL bytea](https://www.postgresql.org/docs/17/datatype-binary.html), [node-postgres: подключение](https://node-postgres.com/features/connecting), [node-postgres: параметризованные запросы](https://node-postgres.com/features/queries).
